# Report: refund-exactly-once

Generated by `npm run report` from a real run of this repo. CI regenerates it and fails if the checked-in copy is stale.

The provider is a fake written for this repo. No real payments, keys or network calls; nothing here is modelled on any particular company's product or API.

## Setup

- runtime: Node 20 or newer (CI runs 20 and 22), tsx, node:test
- database: PGlite (Postgres compiled to WASM), a fresh in-memory instance per run
- variants: `baseline` (naive tool execution) vs `hardened` (exactly-once tool execution)
- random sweep: 40 seeds per variant, 8 tool calls over 5 request keys per run, per-call fault rate 0.4 (timeouts, 5xx, lost responses, crashes), retry budget 3 attempts per call

## Scenarios

Amounts are cents. "moved / recorded" is the provider total vs what the database recorded for the payment.

| scenario                | fault injected                                                                                           | naive: moved / recorded   | naive verdict                            | hardened: moved / recorded | hardened verdict |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------- | ---------------------------------------- | -------------------------- | ---------------- |
| duplicate-tool-call     | the agent emits the same refund call twice (a repeated tool call, or the whole turn retried)             | 8000 / 8000 (want 4000)   | FAIL: provider moved 8000, expected 4000 | 4000 / 4000 (want 4000)    | ok               |
| timeout-after-success   | the provider moves the money but the response is lost; the runtime retries the tool call                 | 8000 / 4000 (want 4000)   | FAIL: provider moved 8000, expected 4000 | 4000 / 4000 (want 4000)    | ok               |
| concurrent-approvals    | the agent and a human approve refunds racing on the same payment (two 7000 refunds on a 10000 payment)   | 14000 / 14000 (want 7000) | FAIL: refunded 14000 on a 10000 payment  | 7000 / 7000 (want 7000)    | ok               |
| crash-after-tool-call   | the runtime dies after the provider moved money, before writing state; the turn is retried after restart | 8000 / 4000 (want 4000)   | FAIL: provider moved 8000, expected 4000 | 4000 / 4000 (want 4000)    | ok               |
| transient-5xx (control) | the provider returns 500 twice, then recovers. Nothing should go wrong in either version                 | 4000 / 4000 (want 4000)   | ok                                       | 4000 / 4000 (want 4000)    | ok               |

## Random sweep

- hardened: 0/40 runs violated an invariant (over-refund, provider vs database drift, payment-total drift, or a refund stuck pending)
- naive: 28/40 runs violated the same invariants

## Mutation checks

Each defence was removed one at a time to confirm it is load-bearing:

- without the idempotency key: timeout-after-success moved 8000 cents where 4000 was intended ("provider moved 8000, expected 4000")
- without the balance guard: concurrent approvals moved 14000 cents on a 10000 payment ("refunded 14000 on a 10000 payment")

## Limits

- The fake provider is a simplified model: idempotency keys are remembered forever and a replay returns the first result. Real providers differ.
- PGlite is a single connection, so the concurrency tests interleave async operations rather than using parallel database sessions. The hardened code is written for real Postgres (unique index, ON CONFLICT, atomic conditional update), but this repo does not test parallel sessions.
- One payment, partial refunds, one currency. No auth, no webhooks, no provider-side failure after acceptance.
- The 0.4 fault rate is chosen to exercise the failure modes, not measured from any production system.
- It is a demonstration, not a payments library.
